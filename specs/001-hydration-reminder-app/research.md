# Research — Wotah (001-hydration-reminder-app)

**Date**: 2026-10-22 · **Input**: [spec.md](./spec.md), `SPEC.md`, `DESIGN-BRIEF.md`, `design/*.html`

Each item follows **Decision / Rationale / Alternatives**. Items marked ⚠️ depend on an on-device
validation (spike) before work builds on them (Constitution › Development Workflow).

## R1. Expo SDK version

- **Decision**: Expo **SDK 57** (patch ≥ 57.0.17, React Native 0.86, React 19.2). Re-evaluate SDK 58 only once it leaves beta.
- **Rationale**: `expo-widgets` became stable in SDK 56, but SDK 56 has a Hermes V1 memory regression with `react-native-reanimated`/`react-native-worklets`. The app uses Reanimated for the bottle animation. SDK 57 fixes the regression and is a non-breaking upgrade from 56. `SPEC.md` asks for "SDK 56+", which 57 satisfies.
- **Alternatives**: SDK 56 (rejected because of the regression); SDK 58 beta (RN 0.88 RC, targets iOS 27; too unstable to start on). SDK 58 adds a new `expo-app-intents` package that could solve R5 without Swift; keep watching it.
- **Inherited requirements**: minimum iOS 16.4 (SDK 56+). Xcode 26.4+ only on the EAS builders.

## R2. Building and testing without a Mac

- **Decision**: **EAS Build** (cloud macOS runners) + a **development build** (`expo-dev-client`) installed on the iPhone via TestFlight or ad-hoc distribution. Day-to-day work runs on Windows with Metro (`npx expo start --dev-client`) and the iPhone on the same network (or `--tunnel`).
- **Rationale**: `expo-widgets`, notification categories with actions and Live Activities do not work in Expo Go. Only a development build contains the Widget Extension generated by prebuild. EAS manages certificates and provisioning profiles without local Xcode.
- **Practices adopted**:
  - **CNG (Continuous Native Generation)**: no committed `ios/` folder; all native config comes from `app.config.ts` + config plugins. In SDK 57, `prebuild` clears native directories, which reinforces this rule.
  - `eas.json` profiles: `development` (dev client, internal distribution), `preview` (internal release via TestFlight) and `production`.
  - Native rebuild only when a native dependency or config plugin changes. JS changes ship via Metro (dev) or **EAS Update** (preview).
  - Register the iPhone with `eas device:create` for ad-hoc builds, or use TestFlight for every build.
  - Use `npx expo install` (never plain `npm i`) for Expo packages; run `npx expo-doctor` in CI.
- **Alternatives**: Expo Go (not viable), cloud-rented Mac (unnecessary), local builds (require a Mac).

## R3. Code structure and isolation of business rules

- **Decision**: one Expo app with three layers:
  1. `src/domain/`: **pure TypeScript**, with no React/React Native/Expo imports. Holds the goal rules, awake window/logical day, reminder planning, mascot expression, streak and PT-BR formatting. It is **functional and deterministic**: the clock is a parameter (`now: Date`).
  2. `src/services/`: platform adapters (SQLite, notifications, Live Activity, haptics). Each implements an interface defined by the domain/use-case layer (ports & adapters).
  3. `src/app/` (Expo Router) + `src/ui/`: screens and components.
- **Rationale**: `SPEC.md` says a possible migration to Swift must be "just translation" (Constitution I). With a pure, dependency-free domain, a rewrite means porting ~10 pure functions with the same table tests (the same cases become `XCTest`). It also lets 100% of the rules be tested on Windows with Jest, without a device.
- **Alternatives**: logic inside hooks/stores (couples to React and makes the port harder); a monorepo with a `@wotah/domain` package (complexity with no gain now; it can be extracted later without code changes).

## R4. Local notifications with the "Bebi 💧" action ⚠️

- **Decision**: `expo-notifications` with a `WOTAH_REMINDER` category and a `DRINK` action (`buttonTitle: "Bebi 💧"`, `opensAppToForeground: false`). Use a `DATE` trigger for each reminder. On every state change, **cancel all reminders and reschedule the whole remaining chain**: today's remaining reminders plus the full chain for the next window (assuming 0 ml).
- **Rationale**:
  - Scheduling the **whole chain** (not just "the next one") means reminders keep arriving inside the window even if JS does not run after a background action or a Live Activity sip. The worst case becomes "one reminder early", not "no reminders".
  - Including the next window covers the following day if the user does not open the app (the day resets at wake time).
  - Volume: with the maximum 6 L goal there are at most 24 per day; today + tomorrow ≤ 48. That is below the iOS limit of 64 pending notifications.
  - The body text ("Faltam {n} copos") is computed at schedule time for each item in the chain, assuming no sips in between, and recomputed on every sip.
- **Risk ⚠️**: the Expo docs do not guarantee that JS runs on iOS when the user taps an action with `opensAppToForeground: false` while the app is **terminated**. `registerTaskAsync` only covers that case on Android, and there are older reports of the listener not firing in the background.
- **Mitigation (layered)**:
  1. A single `handleNotificationResponse()` handler registered at module scope (before the first render) via `addNotificationResponseReceivedListener`. When iOS wakes the app in the background, JS runs the handler.
  2. On cold start and on every return to the foreground: `getLastNotificationResponse()` + dedupe by `request.identifier` (idempotency; see the `processed_event` table in the data model).
  3. Because the chain is already scheduled, a missed sip does not cause extra notifications; at most one reminder arrives "early".
  4. **Native Plan B**: a local Expo Module in Swift (`modules/wotah-native`) implementing `UNUserNotificationCenterDelegate` for the `DRINK` action and writing the sip directly to the App Group SQLite database (see R6). It is adopted only if spike S1 shows sips can be lost (Constitution III).
- **Tapping the body** of the notification (FR-017): the same handler, with `actionIdentifier === DEFAULT_ACTION_IDENTIFIER`. It logs the sip, opens Home and shows the "Desfazer" toast.
- **Alternatives**: scheduling only the next reminder (fragile without background JS); a repeating `TIME_INTERVAL` trigger (ignores the window and goal); remote push (needs a server; out of scope).

## R5. Live Activity / Dynamic Island with `expo-widgets` ⚠️ (main risk)

- **Decision**: `expo-widgets` with `createLiveActivity('WotahDay', …)`, filling the `compactLeading`, `compactTrailing`, `minimal`, `expandedLeading`/`expandedTrailing`/`expandedCenter`/`expandedBottom` and `banner` (lock screen) regions with `@expo/ui/swift-ui` components. Lifecycle:
  - **Start**: when the app opens, if today's goal is not met and `Factory.getInstances()` is empty, call `start(props, url)` with `wotah://home?sip=1` on iOS < 17 (no interactive button), `wotah://home` on iOS 17+.
  - **Update**: `instance.update(props)` on every sip logged in the app.
  - **Goal met**: `update({ celebrating: true })`, then `end('default', props)` with `after(now + 5 min)`.
  - **8-hour expiry**: accepted. The activity is restarted on the next `AppState → active`.
  - `NSSupportsLiveActivitiesFrequentUpdates` is not needed (at most a few dozen updates per day).
- **Countdown to the next reminder**: send `nextReminderAt` (epoch ms) in the props and render it with SwiftUI relative/timer text, so iOS counts by itself without per-minute updates.
- **"Bebi 💧" button (FR-023): confirmed limitation**:
  - An `expo-widgets` button's `onPress` runs in the widget's **isolated runtime**. Its return value becomes the activity's new props, so **the activity itself rises by 250 ml immediately, even with the app terminated**.
  - However, the isolated runtime **cannot reach the app's SQLite database or `expo-notifications`**. The app only learns about the tap via `addUserInteractionListener`, which **only fires while the app process is alive**. In addition, [expo/expo#49828](https://github.com/expo/expo/issues/49828) (listener does not receive interactions on SDK 57) is still open.
- **Chosen approach (user decision, 2026-10-22): Expo-only, with the caveat accepted in the spec** (Clarifications, FR-015, FR-023, SC-005):
  - `onPress` returns `{ ...props, consumedMl: props.consumedMl + 250, pendingSips: props.pendingSips + 1, seq: props.seq + 1 }`.
  - With the app alive, the listener triggers `reconcile()`, which imports `pendingSips` (source `live_activity`), resets them via `update()` and reschedules.
  - With the app terminated, the activity shows the right value, and on the next run the app reconciles by reading the instance's current props via `getInstances()`. The already-scheduled reminder chain (R4) remains valid until then.
  - **Fallback (only if spike S2 shows props cannot be read back, i.e. sips would be lost)**: a local Expo Module in Swift with a `LiveActivityIntent` (iOS 17) that writes the sip to the App Group SQLite database and reschedules the `UNNotificationRequest`s using the same (ported) domain rules. It would be isolated in `modules/wotah-native/` and recorded in the plan's Complexity Tracking. A no-Swift alternative to watch is `expo-app-intents` (SDK 58).
- **Alternatives**: `expo-apple-targets` + hand-written SwiftUI (more control, but contradicts the user's "Expo widgets first" choice); push-to-start/push updates (need a server; out of v1).

## R6. Local storage

- **Decision**: **`expo-sqlite`** (modern sync/async API) with the database file **inside the App Group** (`group.<bundleId>`, the same one `expo-widgets` uses), resolved via `Paths.appleSharedContainers` from `expo-file-system`. The model is an event log of `sip` rows (append + soft delete for undo). Daily totals are derived.
- **Rationale**:
  - History, streak and undo are natural SQL queries, and the sip log with `source` matches the spec's Sip entity.
  - Keeping the database in the App Group lets the native fallback (R4/R5) write to the **same** database without migrating data.
  - Versioned migrations in code with `PRAGMA user_version`.
  - ⚠️ Spike S3 must confirm that `openDatabaseSync(name, options, directory)` accepts the App Group directory. If not, use the default directory in v1 and move the file only if the native fallback is adopted.
- **Preferences** (profile): a single-row `profile` table in the same database, which avoids a second mechanism such as AsyncStorage/MMKV.
- **Alternatives**: AsyncStorage (no queries, and the JSON grows unchecked); MMKV (fast, but another native store that does not help with history); Drizzle ORM (can be added later; for 5 tables plain SQL is simpler).

## R7. UI state

- **Decision**: **Zustand** as a thin read store (`profile`, `today`, `week`, `nextReminderAt`, `toast`). All writes go through **use cases** (`registerSip`, `undoLastSip`, `updateProfile`), which write to SQLite and then re-sync effects (notifications, Live Activity) in a single `syncSideEffects()`.
- **Rationale**: a single write path guarantees the "every sip, by any means, reschedules" rule. The store is disposable and can be rebuilt from the database at any time (cold start or return to the foreground).
- **Alternatives**: Context + useReducer (broad re-renders), Redux Toolkit (too much ceremony for 3 screens), TanStack Query (meant for remote data).

## R8. Navigation

- **Decision**: **Expo Router** (file-based), with `(onboarding)` and `(main)` groups and a redirect based on `profile.onboardingCompleted`. The deep link `wotah://home?sip=1` is used as the Live Activity tap URL on iOS < 17 (no interactive button): opening it logs a sip (`source: 'live_activity'`) and shows the "Desfazer" toast, keeping logging at one tap (Constitution VI).
- **Rationale**: it is the Expo template default. In SDK 56+ it no longer depends on React Navigation, and deep linking comes built in.
- **Alternatives**: React Navigation directly (more configuration, no gain).

## R9. Bottle mascot animation

- **Decision**: port the `Mascote` component from `design/Wotah Sistema.html` (SVG viewBox `-30 -30 260 320`) to **`react-native-svg`**, animated with **`react-native-reanimated` 4**:
  - Water level: `waterY = 278 − min(p,1) × 214`, animated with an overshooting `withSpring` (equivalent to the design's 1.1 s `cubic-bezier(.34,1.45,.55,1)` with a 280 ms delay).
  - Two waves (`translateX`) loop forever in opposite directions (2.6 s and 3.4 s, linear).
  - Squash & stretch of the body from the feet (`scale 1.06/.93 → .97/1.05 → 1`, 650 ms, 300 ms delay), only when the level rises.
  - A drop flies from "+" to the bottle neck (0–520 ms). The button sinks to 92% (0–150 ms) with a light `expo-haptics` tap. Confetti (~1 s) plus a success haptic when the goal is met.
  - The expression switches mid-jump when progress crosses 25% or 100%.
  - **Reduce Motion** (`useReducedMotion`): no jump, drop or confetti; only the level, expression and number change.
  - Repeated taps mid-animation add sips; the spring target updates without restarting the animation.
- **Rationale**: the design's SVG is already the source of truth (paths, colors, expressions), and `react-native-svg` renders the same paths. Reanimated runs the animation on the UI thread, which meets SC-006.
- **Alternatives**: Lottie/Rive (would require redoing the art in another tool); Skia (more power, but an extra dependency for a simple scene).

## R10. Design system from `Wotah Sistema.html`

- **Decision**: the tokens extracted from `design/Wotah Sistema.html` become `src/ui/theme/tokens.ts` (contract in [contracts/design-tokens.md](./contracts/design-tokens.md)). The other HTMLs (`Telas`, `Live Activity`, `Widgets`) are the **visual reference** for screens and states (Constitution V). Light/dark follows `useColorScheme()` (FR-033).
- **Fonts**: **Fredoka** (500/600; titles and numbers with `tabular-nums`) and **Nunito** (400/700/800; body, buttons and captions) via `expo-font` + `@expo-google-fonts/*`, embedded by the `expo-font` config plugin (no loading flash).
- **On system surfaces** (Live Activity): the widget runtime does not load the app's fonts automatically. Use the system font with `design: rounded` (SF Rounded), which has the same spirit, and only try Fredoka if `expo-widgets` allows bundling fonts into the extension.
- **Mascot on system surfaces**: the drop with a face becomes SwiftUI shapes or pre-rendered PNGs (4 expressions, a few levels) written to `widgetsDirectory` and referenced from the props.
- **Alternatives**: NativeWind/Tailwind (fine, but there are few tokens and the design uses inline styles; a `StyleSheet` with typed tokens is enough); Tamagui (too heavy for the scope).

## R12. Testing and quality

- **Decision**:
  - **Jest + `jest-expo`** for the domain and use cases, written test-first (Constitution IV), as table tests covering every acceptance scenario and numeric edge case in the spec, with an injected clock.
  - **`@testing-library/react-native`** for critical UI interactions (Desfazer toast, long-press "+", onboarding).
  - **Service tests** with `expo-notifications`/`expo-widgets` mocks that check the scheduling *plan* (what gets cancelled and scheduled).
  - **Manual on-device validation** (script in [quickstart.md](./quickstart.md)) for notifications, Live Activity and Dynamic Island. Optional: Maestro via EAS Workflows on an iOS simulator for UI flows.
  - TypeScript `strict`, ESLint (`eslint-config-expo`) and Prettier; `expo-doctor` in CI.
- **Alternatives**: Detox (needs a Mac locally).

## R13. Time zone, clock and day rollover

- **Decision**: every calculation uses the device's current local time (`now`). The logical day is identified by the local date of the **last wake time ≤ now** (`dayKey = 'YYYY-MM-DD'`). Sips store `occurredAt` (epoch ms, UTC) plus the `dayKey` computed at logging time. On return to the foreground and on time zone/clock changes (`AppState` + a `dayKey` check), everything is recomputed and rescheduled.
- **Rationale**: covers the "window crossing midnight", "day rollover" and "time zone change" edge cases without a heavy date library. `date-fns` can help with formatting, but the domain uses minutes-of-day arithmetic.

## R14. Accessibility (Constitution VI)

- **Decision**: every interactive control gets a PT-BR `accessibilityLabel`/`accessibilityHint` (e.g., "+" → "Registrar um copo de 250 ml"). Touch targets are ≥ 44 pt. Text and token pairs are checked against WCAG AA (`ink`/`ink2` on `bg`/`surface`, in both themes). Reduce Motion is honored per R9. Text scales with Dynamic Type up to the large (non-accessibility) sizes, with layouts tested at that size. The mascot gets one summarizing label (e.g., "Garrafa com 1,25 de 2 litros, animada").
- **Rationale**: the constitution sets the "essential" accessibility bar as a gate.
- **Alternatives**: none; this is a non-negotiable minimum.

## Implementation findings (2026-10-22, from installed `expo-widgets` 57.0.27 source)

Read in `node_modules/expo-widgets/ios/Widgets/AppIntent.swift` and `WidgetsModule.swift` during
Phase 2. They contradict part of R5 and must be confirmed by spike S2 on the device:

- **Live Activity buttons do not evaluate `onPress`.** Home-screen widget buttons use
  `WidgetUserInteraction`, which runs the `onPress` JS in the widget runtime and stores the new props
  in the App Group. Live Activity buttons use `LiveActivityUserInteraction` (a `LiveActivityIntent`),
  whose `perform()` only posts an in-process `NotificationCenter` event. The activity does **not**
  change by itself; the app must call `update()`.
- **There is no props read-back.** `LiveActivity` exposes only `getId`, `update`, `end` and
  `getPushToken`, so the "read `pendingSips` from `getInstances()`" reconciliation in R5 is not possible.
- **Delivery depends on the app process.** `LiveActivityIntent.perform()` runs in the app process
  (iOS launches it in the background if needed). The event reaches JS only if a listener is already
  observing. When the app is suspended, this should work. When the app was terminated, the event is
  likely posted before the JS bundle registers the listener, so the tap would be lost.
- **Consequence**: with Expo only, the Live Activity "Bebi 💧" works while the app process is alive
  and is likely lost when it was terminated (the activity simply does not change, so nothing wrong is
  displayed). Making it reliable needs native code that persists the interaction (Phase 9 fallback,
  or a small local module that queues interactions in the App Group for JS to drain on start).
- **Spike S2 (updated)**: measure (a) app suspended → tap logs exactly once; (b) app terminated →
  is the tap delivered or lost? T073's parity test and T078's `onPress` props become moot for
  Live Activities; they still apply to a v2 home-screen widget.
- **Reminder at bedtime (2026-10-22, during T059)**: the analysis-era rule "the 8th reminder falls at
  bedtime and is excluded" broke FR-019/AS-3.7 (with 1 glass left, the only reminder always lands at
  bedtime). The chain now allows `t ≤ bedtime`; the spec only forbids reminders *after* bedtime.
  AS-3.1 therefore yields 8 reminders (09:45 … 22:00), matching "14 h ÷ 8 copos".
- **Native fallback adopted (2026-10-22, owner decision)**: `modules/wotah-native` (Swift) observes
  expo-widgets' interaction notification from `subscriberDidRegister` (earliest point in the app
  process) and queues each tap in the App Group; JS drains it on boot/foreground with the same
  idempotency keys as the live listener. When iOS launches the terminated app for the
  LiveActivityIntent, the JS bundle boots in the background and processes the queue, rescheduling
  reminders and updating the activity. Spike S2(b) now validates this path.
- **SDK 58 (2026-10-22, owner decision; supersedes R1's "SDK 57")**: SDK 58 went stable on 2026-10-16
  (RN 0.88, React 19.3, iOS 27). Changes applied: Expo Router 58 (`Stack.Protected` with explicit
  `redirectTo`, `initialRouteName` removed, `useRouter()` instead of the module-level `router`),
  Jest resolver from `react-native-reanimated/jest/resolver` (Worklets 0.13), removed the unused
  `expo-symbols`. expo-widgets 58 keeps the same `onExpoWidgetsUserInteraction` notification and
  `ExpoWidgetsAppGroupIdentifier` key, so `modules/wotah-native` is unchanged. Caveat: the App Store
  Expo Go supports SDK 58 only "within a few weeks"; until then, test on a development build.
